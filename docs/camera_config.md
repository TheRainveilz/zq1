**记录格式（已实测确认，控制帧与图像块共用同一结构）**：

| 偏移 | 内容 |
|---|---|
| `+0` | 魔数 `AA 55 AB CD` |
| **`+7`** | **u16 小端 = 载荷长度**——唯一可靠的长度字段 |
| `+9` | `0x01` = 控制帧（JSON 载荷）；`0x14` = 图像数据块 |
| `+10` | `0x00` = 控制帧；`0x03` = 图像块 |
| `+13` | u16 小端 = 图像块序号 `0..N` |
| `+17` | u16 小端 = 随图结果 JSON 的长度（控制帧上等于载荷长度） |
| `+50` | 载荷 |
| 尾 | 2 字节：`(sum(头 50 字节) + sum(载荷)) & 0xFF`，再跟一个 `0x00` |

⚠ **偏移 4 的大端 u32 只在纯 JSON 控制帧上等于载荷长度**，图像块上恒为 20，偏移 16 的 u16 读出来是 107，
都对不上——早期把它当长度字段是错的，现已改用 `+7`。整帧 = 50 + 载荷 + 2（39 字节 JSON → 91 字节整帧）。

**保活**：只读连上去不回话，相机推 5~6 条 `HeartBeat` 就主动断开。必须约 1 s 回一条
`{"CommuniInfo":{"PortCode":"Smsocket3"},"Order":"HeartBeat"}`。算法里是 `CAM_HEARTBEAT_S` 那个线程。

### 1.8.3 图像格式：1280 × 800 无压缩 8 位灰度（直连实测确认）

不是 JPEG——雕出的 `FFD8..FFD9` 段全部 `cv2.imdecode` 失败，那些 `FFD8FF` 是过曝 raw 数据里的巧合。
一帧图由**连续的图像块**拼成，按 1.8 的记录格式逐块解开即可：

| 项目 | 实测 | 依据 |
|---|---|---|
| 块数 / 帧 | **788**（序号 0..787 连续无缺） | 直连抓的 4 MB 流里逐块走通，序号 `+13` 严格递增 |
| 常规块载荷 | **1300 字节** | `+7` 长度字段；整条记录 50 + 1300 + 2 = 1352 字节 |
| 末块载荷 | **1263 字节**（短于常规块 = 帧尾标志） | 788 号块的 `+7` 读出 1263 |
| 块 0 载荷 | 结果 JSON（`+17` 给长度，实测 363）**+** 像素 | 只有 0 号块带 JSON，其余全是像素 |
| **像素合计** | **1024000 字节 = 1280 × 800** | 787 × 1300 + 1263 − 363 = 1024000，与传感器自报 `ImageResolution` 完全一致 |
| 单帧实测 | 均值 76.3，饱和(≥250) 8.20% | 见第 3 节 |
| 预览流量 | 403 MB / 215 s ≈ 1.9 MB/s | 远低于百兆链路上限，预览是被限速的 |

> 早期从 pcap 里量出的「行跨距 1332」是**丢包导致的假结论**（那次抓包 CAM→PC 缺 76.3%，
> 把不连续的片段接起来量的）。1332 = 1300 + 32 更像是把每块的头尾算进去了。
> 按记录格式解开后一帧恰好 1024000 字节，reshape 成 800 × 1280 图像干净无错位，不需要任何补偿。

**这条对算法是好事**：直连拿到的是无压缩灰度，4.3 那一整节
（`MARK_CIRCULARITY_MIN` / `MIN_VALID_MARKS` / `RING_MIN_CONTOUR_PTS` 随 JPEG 质量漂）的自变量直接消失。

⚠ **但取景/尺寸和标定样本不是一回事**：标定用的样本 JPEG 是 **1216 × 1024**（MJ 存图的取景），
直连帧是 **1280 × 800**，垂直方向少 22%。所以第 3 节的几何标定值（兜孔半径 50.7 px、节圆 396.9 px、
中心 (654.4, 475.2)）**不能直接搬到直连帧上**，要在直连取景下重标一次，见第 5 节。

三条取图路，按当前状态：

1. **`camera` 直连（在用，推荐）** —— 10001 私有协议，`--mode camera`。相机把无压缩灰度帧直接推过来，
   不落盘、不过 JPEG。上线用 **IO 外部硬触发**（`CAM_TRIGGER_ORDER = "external"`）：算法只保活、
   被动等帧，一个触发沿 = 一件 = 一帧，曝光时刻由工装决定；台上调试可切 `--trigger MainRunOnce`
   走软触发。实测 0.3 ~ 0.65 s/帧（帧到手→判完）。实现见
   `thrust_cage_flange_inspect.py` 的 `Wtx10001Source`
2. **`watch` 存图模式（备用）** —— MJ_Aisensor 照常存图，算法监视存图目录。
   好处是压缩质量与标阈值用的样本完全一致；代价是多一次落盘，且
   ⚠ **依赖 MJ 真的在存图**：2026-09-05 实测点 3 次「执行」，存图目录里一张新图都没多，
   上线前先确认「点一次执行 → 目录里多一张图」这条链是通的，否则算法会一直空等
3. **FTP / SSH 拉图** —— 需要厂家账号密码，未走通

> 169.254.x.x 也丢给代理，症状是莫名的 `ReadTimeout` 而不是连接失败。算法头部
> `HTTP_USE_SYSTEM_PROXY = False` 就是为此，别改回 True。

## 4. 阈值与成像条件的绑定关系

按 `r`（兜孔半径）比例写的常量换成像条件仍成立：拐角角度、距离比、压痕半径比、
环带范围、聚类间隔。**下面这些不成立，相机一改就要重标**：

### 4.1 随工作距离 / 分辨率 / binning 变化

| 常量 | 当前值 | 说明 |
|---|---|---|
| `HOLE_R_MIN_RATIO` / `HOLE_R_MAX_RATIO` | 0.030 / 0.065 | 孔半径 ÷ 图宽。WD 或分辨率一变，这个比例就偏。⚠ **直连取景实测 0.0318，离下限 0.030 只剩 6% 余量**（见 3.1）；工件再远一点或再小一点，兜孔就被整体筛掉 → `NG_HOLE_NOT_FOUND` |
| `HOLE_MIN_DIST_RATIO` | 0.060 | 相邻孔心最小间距 ÷ 图宽 |
| `OUTER_R_MIN/MAX_RATIO` | 0.18 / 0.60 | 兜底定位用的大圆半径范围 |

### 4.2 随曝光 / 增益 / 光源变化

| 常量 | 当前值 | 说明 |
|---|---|---|
| `REFINE_MIN_CONTRAST` | 12 | 孔内/台面灰度差下限。曝光降太多会让暗区的孔被整体丢弃 |
| `HOLE_HOUGH_P1` | 120 | Canny 高阈值，跟边缘梯度强度绑定 |
| `HOLE_HOUGH_P2` / `_FALLBACK` | 55 / 32 | 累加器阈值。孔找不全先动 fallback |
| `FLANGE_HOUGH_P2` | 20 | 同心 Hough 找翻边圆 |
| `MARK_HOUGH_P2` | 16 | 拐角压痕的形状级预筛，光源换极性后最容易失效 |
| `CLAHE_CLIP` / `CLAHE_GRID` | 2.0 / (8,8) | 台面纹理很平的图上 CLAHE 会放大噪点 |

### 4.3 随 JPEG 质量变化（**只在 `watch` 模式下是变量；`camera` 直连是无压缩灰度，本节自变量消失**）

| 常量 | 当前值 | 说明 |
|---|---|---|
| `MARK_CIRCULARITY_MIN` | 0.75 | 只负责剔毛刺碎轮廓，**不是正反鉴别量**（反面误检圆度 0.883 > 正面 29/30）。压缩率一降边缘发毛，正面圆度整体下移会减少有效压痕数——受害的是下一行 |
| `MIN_VALID_MARKS` | 2 | 4 个拐角要求至少 2 个有效，**真正的鉴别量**。正面 30 个压痕里有 5 个只在 16 个阈值组合中的 1 个上过门（全在 r ≥ 0.497），压缩后先掉这批。⚠ 降这个比降圆度阈值危险得多：反面已有 1 个误检压痕，降到 1 直接判 OK |
| `RING_MIN_CONTOUR_PTS` | 24 | 压缩块效应会打断轮廓 |

### 4.4 随取景位置变化

| 常量 | 当前值 | 说明 |
|---|---|---|
| `HOLE_CHECK_COUNT` | 2 | 选孔按"ROI 完整在视场内 → 4 拐角完整数 → 孔壁对比度"排序。可见孔变少时余量下降 |
| `MIN_HOLE_COUNT` | 2 | 有效孔少于 2 直接 NG。反面样本 18 个兜孔只检出 4 个，**余量只有 2 个孔**；再少就会退化成 `NG_HOLE_NOT_FOUND`（定位失败），那种 NG 不算特征判出来的 |

### 4.5 与成像条件无关，但已知标得过宽

`MARK_R_RATIO_RANGE = (0.28, 0.55)` 是按 `r` 的比例写的，换相机仍成立——但**"仍成立"不等于
"标得对"**。这个范围跨了近 2 倍，Hough 会锁到比压痕更大的结构（翻边边缘之类）上：

- 反面样本的 2 个误检/擦边命中（r = 0.53 / 0.482）**全在 ≥0.45 r**
- 正面 5 个阈值裕度只有 1/16 的压痕，**全在 r ≥ 0.497**
- ⚠ **直连取景下上界能收的空间比想象的小**：2026-09-05 那个判 OK 的直连帧，两个受检孔各只有
  2 个有效压痕，半径比分别是 **0.33 和 0.44**——上界收到 **0.42 就直接把正面翻成 NG**，
  收到 0.46 也只剩 0.02 的余量

收窄上界是提特异性最直接的一手（能把反面误检压到 0 个），但会吃掉正面每孔的压痕余量——
按实测，上界收到 0.46 会让正面孔 #1 从 4 个压痕掉到正好 2 个，一点不剩。这是在正反两边的余量
之间做交换，而改善成像是同时抬高两边。**先把 1.2 那条饱和亮带压掉、在直连取景下重拍，再定这个范围。**

## 5. 换相机 / 改参数 / 换取图方式后的复检清单

按顺序做，每步不过就别往下走：

0. **（换到 `camera` 直连时先做这步）** 确认取图链路本身通：
   `python thrust_cage_flange_inspect.py --mode camera --limit 3 --debug`
   看是否每帧都打印出定位信息（打印得出来就说明 1280×800 帧完整解开了）。⚠ 这一步只验证取图，
   **不看 OK/NG**：直连取景还没标定，工件没摆正时判 NG 是正常的
0b. **确认触发是 IO 硬触发，不是自由连跑**（✅ 2026-09-05 已通过一次；每次在 MJ 里动过触发设置、
   或用过 `--trigger MainRunOnce` 之后都要重做）：MJ 里「外部触发 + 触发源 IO + `LINE_IN0` +
   上升沿 + 防抖 10000 μs + 延迟 0 ms」，且**方案处于运行态**，然后跑上面那条命令**不放件**——
   应当停在 `[INFO] 等触发信号中...` 一直不出帧（每 30 s 打一行，说明链路和心跳都活着）；
   再给 N 次工装到位信号，应当**恰好多出 N 帧**。2026-09-05 实测：空等 92 s 零帧，给 3 次得 3 帧。
   若不给信号也在刷帧，说明触发源又变回软触发/自由运行，回 MJ 再改（算法侧改不了，见 1.8.2）；
   若给了信号也不出帧，先看方案是不是被上一轮软触发的 `StopRun` 停住了
1. `python thrust_cage_flange_inspect.py --dir docs/ref --holes 0 --debug`
   跑基准图，对照第 3 节数字（孔半径、节圆残差、孔壁对比度、压痕圆度），注意用同一取景那一组
2. 看叠加图：蓝圈节圆是否套住所有孔心 → 青圈孔 ROI 是否套住翻边 → 绿框拐角是否压在压痕上
3. `python thrust_cage_flange_inspect.py --calib --dir docs/ref`
   核对 `CORNER_SPEC` 与 `MARK_R_RATIO_RANGE`，偏差超 5° / 0.1 就抄新值进头部
4. 正面样本至少 20 张，要求**全部判 OK**，且每张有 ≥2 个孔双特征全过（留余量）
5. 反面样本至少 20 张，要求**全部判 NG**，且 NG 代码是 `NG_NO_FEATURE`
   （出现 `NG_HOLE_NOT_FOUND` 说明孔都没找到，是定位问题不是特征问题，不算通过）
6. 边界样本（漏冲、油污、毛刺）逐张看叠加图，确认判定原因和肉眼一致
7. 全部通过后，更新本文件第 1、3 节数值和第 6 节变更记录，连同头部常量一起提交

> 第 4、5 步的样本文件名要带 `正`/`反`（或 `front`/`back`）：`dbg_report.py` 的 `guess_label()`
> 靠文件名推真值，推不出来 `--sweep` 的阈值网格只会显示 `0/0`，读不出推荐阈值。
> 2026-09-04 的两张样本（`1_4256379.jpg` / `8_4222844.jpg`）就是这种情况。
> 走 `camera` 直连时帧名是 `CAM#序号` / `CAM_<相机时间戳>`，同样推不出真值——**不用重命名**，
> 按轮次分目录采、分析时强制真值即可：
>
> ```bash
> python thrust_cage_flange_inspect.py --mode camera --collect "D:\zq\samples\直连_正"
> python dbg_report.py --dir "D:\zq\samples\直连_正" --holes 0 --sweep --truth front
> ```
>
> `--collect` = 存**原始帧**（不划线）+ PNG 无损 + OK 帧也存，正是 dbg_report 要的输入：存叠加图
> 会让它去分析图上画的线条，存 JPEG 会把 4.3 节那个压缩自变量又加回来。
> 铁律：**一轮只放一类件**，`--truth` 是整目录一刀切的。反面轮把路径里的「正」改成「反」。
